# 健康监测 App 技术选型文档

日期：2026-06-07  
状态：待评审

## 1. 文档目标

本文档用于明确健康监测 App MVP 阶段的客户端技术选型、工程分层、平台边界与开发里程碑，作为产品设计文档的技术补充。后续实现计划、任务拆解与代码开发默认以本文档为技术基线。

## 2. 选型结论

健康监测 App 的客户端主路线定为：

`Flutter 负责产品层 + 必要原生插件桥接负责高权限与平台差异能力`

该路线的基本判断是：

- 页面、导航、状态管理、规则引擎、简报生成、本地存储、文案逻辑尽量放在 Flutter 共享层。
- 传感器采集细节、后台任务、系统高权限能力、iOS 与 Android 差异化 API 通过原生插件或 Platform Channel 处理。
- 不将架构建立在“所有能力都可由现成 Flutter 插件稳定解决”的假设之上。

## 3. 为什么不选纯 Flutter 插件优先

纯 Flutter + 通用插件的路线虽然启动快，但不适合作为本项目的长期主架构，原因如下：

- 本产品不是普通内容型 App，而是传感器、权限、后台采集较多的系统能力型产品。
- 数字生活习惯分析、后台任务、位置策略、部分噪音采样能力都可能受到平台权限与系统策略限制。
- iPhone 与 Android 在系统能力边界上并不对称，单纯依赖 Dart 插件层容易在中后期出现重构成本。

因此，Flutter 更适合作为：

- 共享产品壳
- 共享业务核心
- 共享交互与状态流

而不是承担所有平台能力接入责任。

## 4. 客户端技术栈

### 4.1 基础框架

- Flutter
- Dart
- Material 3

选择理由：

- 双平台 UI 共享效率高
- 开发速度快，适合 MVP 快速验证
- 对页面、业务编排、状态管理和本地数据处理支持成熟

### 4.2 状态管理

- Riverpod

选择理由：

- 适合大量异步状态与派生状态管理
- 比简单 Provider 更适合复杂业务编排
- 比 Bloc 更轻，首版上手和演进成本更均衡

建议纳入 Riverpod 管理的状态：

- 权限状态
- 平台能力状态
- 今日指标状态
- 每日简报状态
- 提醒记录状态
- 用户设置状态

### 4.3 路由

- GoRouter

选择理由：

- 声明式路由更清晰
- 适合 onboarding、权限引导、设置页、详情页等多页面演进
- 与 Riverpod 配合自然

### 4.4 本地存储

- Isar

选择理由：

- 本项目数据并非简单键值对，而是结构化记录
- 适合存储每日指标、提醒记录、简报快照、状态片段和设置项
- 相比纯 KV 方案，更适合历史记录查询与后续扩展

### 4.5 网络层

- Dio

选择理由：

- 首版虽以本地优先为主，但后续仍可能需要账号、配置同步、简报备份与埋点上报
- 统一网络层能降低后续接后端时的迁移成本

### 4.6 日志与调试

- logger

选择理由：

- 传感器类产品需要更强的数据链路排查能力
- 有助于快速定位页面层、状态层、桥接层与原生层问题

## 5. 传感器与系统能力接入策略

### 5.1 首选 Flutter 插件接入的能力

优先尝试通过成熟插件接入：

- 加速度计与陀螺仪：`sensors_plus`
- 位置能力：`geolocator`
- 通用权限请求：`permission_handler`

原因：

- 这些能力在双平台上的基础接入相对成熟
- 适合 MVP 快速搭建基础能力闭环

### 5.2 预留原生桥接的能力

从一开始就应假设以下能力可能需要原生实现或原生补强：

- Android Usage Stats
- iPhone 屏幕使用与应用类别相关能力验证
- 后台采集调度
- 麦克风环境噪音分级采样
- 更可靠的持续传感器流管理

处理原则：

- Flutter 层只依赖统一服务接口
- Android 与 iOS 各自实现高权限与高差异能力
- 平台差异通过统一状态模型与能力矩阵消化，不直接暴露到页面层

## 6. 原生桥接方案

推荐采用：

- MethodChannel
- EventChannel

建议职责划分：

- MethodChannel：一次性请求、聚合结果获取、权限触发、能力查询
- EventChannel：持续传感器流、状态变化流、后台采集事件流

设计原则：

- Flutter 不直接消费原始平台结构
- 原生侧返回统一后的事件模型或聚合结果
- 所有桥接协议都应有明确字段定义和测试约束

## 7. 工程分层

项目建议采用以下五层结构：

### 7.1 展示层

负责：

- 首页今日概览
- 每日简报页
- 提醒记录页
- 权限引导页
- 设置页

要求：

- 只处理展示与交互
- 不直接处理传感器逻辑

### 7.2 应用状态与业务编排层

负责：

- 权限状态管理
- 指标状态管理
- 简报状态管理
- 提醒状态管理
- 页面与数据刷新联动

要求：

- 使用 Riverpod 管理状态
- 统一编排感知结果到页面结果的流转

### 7.3 领域模型与规则引擎层

负责：

- 指标模型
- 状态模型
- 事件模型
- 建议模型
- 规则阈值
- 简报生成逻辑
- 提醒触发逻辑

要求：

- 尽量保持纯 Dart
- 与 Flutter UI 解耦
- 优先覆盖单元测试

### 7.4 感知适配层

负责：

- 定义 Flutter 侧统一服务接口
- 接收插件或原生桥接返回的数据
- 转换为统一状态模型

要求：

- 不向上暴露平台细节
- 为 iPhone / Android 降级策略提供统一出口

### 7.5 原生桥接层

负责：

- Android 与 iOS 的系统能力接入
- 后台任务调度
- 高权限能力处理
- 平台特殊限制适配

要求：

- 按能力模块分组实现
- 不将多个不相关能力混在单一桥接文件中

## 8. 推荐目录结构

### Flutter 共享层

- `lib/app/`
  - 应用入口、主题、路由、全局 Provider
- `lib/core/`
  - 常量、日志、时间工具、错误封装
- `lib/domain/`
  - 业务模型、枚举、值对象
- `lib/features/`
  - `overview/`
  - `daily_brief/`
  - `reminders/`
  - `permissions/`
  - `settings/`
- `lib/rules/`
  - 规则引擎
- `lib/services/`
  - Flutter 侧服务抽象接口
- `lib/platform/`
  - Platform Channel 封装与平台能力适配
- `lib/storage/`
  - Isar collection 与 repository
- `lib/widgets/`
  - 共享 UI 组件

### 原生层

- `android/`
  - 按 `motion`、`usage`、`location`、`noise`、`permissions`、`background` 分组
- `ios/`
  - 按 `motion`、`usage_capability`、`location`、`noise`、`permissions`、`background` 分组

## 9. 统一数据流

推荐采用如下数据流：

`原生/插件采集 -> platform 适配 -> services 输出统一模型 -> domain 聚合 -> rules 生成建议 -> features 渲染页面`

该数据流的优势：

- 页面不直接接触原始平台数据
- 原生实现变动时，业务层稳定性更高
- 规则引擎可以脱离 UI 单独测试
- 平台降级策略可以集中在 service / platform 层处理

## 10. 平台边界与降级策略

### 10.1 Android

Android 更适合承载以下能力：

- 更细的活动识别与传感器采样
- Usage Stats 驱动的应用类别偏好分析
- 后台任务与前台服务组合
- 更强的数字生活习惯摘要能力

### 10.2 iPhone

iPhone 需要保守处理以下能力：

- 应用类别偏好分析
- 屏幕使用细粒度能力
- 长时后台采集

因此首版必须预置能力降级：

- Android：支持更完整的数字生活习惯摘要
- iPhone：至少支持查看频率、活跃时段、屏幕活跃时长等替代指标

该差异不是 Flutter 问题，而是平台权限边界问题。

## 11. 测试策略

建议至少分三层：

### 11.1 纯 Dart 单元测试

重点覆盖：

- 指标聚合
- 状态识别逻辑
- 规则引擎
- 简报生成逻辑

这是本项目最优先的测试层。

### 11.2 Flutter Widget 测试

重点覆盖：

- 首页关键指标展示
- 简报页核心卡片
- 提醒记录页与权限引导页

### 11.3 平台桥接与集成测试

重点覆盖：

- Flutter 与 Android / iOS 桥接协议一致性
- 能力矩阵与降级逻辑
- 权限拒绝时的降级运行行为

## 12. 开发里程碑

### 里程碑 1：产品壳与共享业务骨架

输出：

- Flutter 工程初始化
- Riverpod、GoRouter、Isar 接入
- 首页、每日简报页、提醒记录页骨架
- 规则引擎第一版
- 用模拟数据跑通页面

### 里程碑 2：基础感知能力接入

输出：

- 加速度计与陀螺仪接入
- 基础位置接入
- 权限申请主流程
- 活动与姿势基础识别

### 里程碑 3：规则引擎与提醒闭环

输出：

- 久坐提醒
- 步数激励
- 低头用机建议
- 移动中看屏提醒
- 提醒记录落库

### 里程碑 4：环境与数字生活习惯能力

输出：

- 环境噪音等级摘要
- 手机查看频率
- 深夜使用时段
- Android 应用类别偏好
- iPhone 可行替代能力

### 里程碑 5：后台采集、稳定性与隐私打磨

输出：

- Android 后台采集策略
- iPhone 可行后台刷新策略
- 权限文案与隐私说明页
- 电量优化与错误日志
- 拒绝权限后的降级运行验证

## 13. 本阶段技术结论

当前最适合健康监测 App MVP 的技术路线，不是纯插件型 Flutter 项目，也不是完全原生双端，而是：

`Flutter 产品壳 + Dart 业务核心 + 原生能力适配层`

该结构可以兼顾：

- 首版开发效率
- 双平台体验一致性
- 复杂系统能力的可控接入
- 后续能力扩展与平台差异收敛

## 14. 下一步建议

在本文档确认后，后续应按以下顺序推进：

1. 先校正产品 spec 与实现计划中的技术栈描述，使其与 Flutter 路线一致
2. 基于本文档输出 Flutter 版实现计划
3. 先做平台能力验证闸门，再开始正式编码
